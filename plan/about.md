GrainSaathi(backend server for GrainSaathi web application) is a secure, scalable, and feature-rich backend for the GrainSaathi web application that aims to simplify and add uniformity in agriculturural buying and selling space(market) . The platform is resposible for seamless trade process between different stakeholders of market.

## gs_contract & sell_contract Model

The core business entity of GrainSaathi. This is the virtual agreement flow between buyer and seller.

### gs_contract (proposal/offer)

- Created by: Farmer (to a buyer) OR Trader/Enterprise (to another enterprise)
- Fields:
  - id (auto-increment)
  - cropName (string)
  - quantity (float, in quintals)
  - pricePerQuintal (int, stored in paise)
  - totalAmount (computed: quantity × price)
  - senderId (the one creating the contract)
  - senderRole (kisaan / vyapari / organisation)
  - receiverId (the buyer)
  - receiverRole (vyapari / organisation)
  - status: PENDING | ACCEPTED | REJECTED | CANCELLED | EXPIRED
  - expiresAt (DateTime — contract offer expires after X hours)
  - message (optional note from sender)
  - createdAt, updatedAt

### sell_contract (finalized agreement)

- Created automatically when a gs_contract is ACCEPTED by the receiver.
- Fields:
  - id (auto-increment)
  - gsContractId (FK to gs_contract)
  - cropName, quantity, pricePerQuintal, totalAmount (copied from gs_contract)
  - sellerId, buyerId
  - status: ACTIVE | COMPLETED | DISPUTED | CANCELLED
  - printedAt (DateTime — when the physical copy was generated)
  - completedAt (DateTime — when actual transaction happened)
  - createdAt, updatedAt

### Contract Flow:

```
Farmer creates gs_contract → Buyer receives notification (SSE)
→ Buyer accepts → sell_contract is created → Both parties can print it
→ Physical transaction happens → Mark as COMPLETED
```

## Database Schema (Prisma Models)

### Existing Models:

- **Kisaan** — Farmer user (name, email, password, phone, address, lat/long, refreshToken)
- **Vyapari** — Trader user (same + gstNumber, registrationStatus: PENDING/ACCEPTED/REJECTED)
- **Organisation** — Enterprise user (same + gstNumber)
- **KisanVyapari** — Many-to-many join: Kisaan ↔ Vyapari
- **KisanOrganisation** — Many-to-many join: Kisaan ↔ Organisation
- **OrganisationVyapari** — Many-to-many join: Organisation ↔ Vyapari
- **OrganisationOrganisation** — Many-to-many join: Org ↔ Org (buyer/seller)
- **RegistrationTaskTicket** — Admin review tickets (status: PENDING/IN_PROGRESS/RESOLVED/REJECTED/FAILED)

### Models to Add:

- **Crops** — Crop listings (cropName, priceInPaise, traderId?, organisationId?, deletedAt for soft-delete)
- **Receipt** — Transaction receipts (cropId, cropPrice, farmerId, cropQuantity)
- **GsContract** — Contract proposals (see gs_contract model above)
- **SellContract** — Finalized contracts (see sell_contract model above)
- **Admin** — Admin user (name, phone, email, password, role, isActive, createdBy superAdminId)
- **SuperAdmin** — SuperAdmin user (name, phone, email, password, creds)
- **ChatRoom** — Enterprise-to-enterprise chat rooms (linked to a sell_contract)
- **ChatMessage** — Individual messages (roomId, senderId, content, type: TEXT/IMAGE/FILE, fileUrl, createdAt)
- **Document** — Uploaded verification docs (userId, userRole, fileUrl, fileType, status: PENDING/VERIFIED/REJECTED)
- **Notification** — Persistent notifications (userId, userRole, type, title, body, isRead, createdAt)
- **CropPriceHistory** — Price change log (cropId, oldPrice, newPrice, changedAt)

## Error Handling

### Standard Response Format

```json
// Success
{ "statusCode": 200, "data": {...}, "message": "success message" }

// Error
{ "statusCode": 400, "data": null, "message": "error description", "success": false }
```

### Utility Classes

- **ApiError** — Custom error class with statusCode and message
- **ApiResponse** — Consistent success response wrapper
- **AsyncHandler** — Wraps async route handlers to catch errors automatically

### HTTP Status Codes Used

| Code | Meaning                             |
| ---- | ----------------------------------- |
| 200  | Success                             |
| 400  | Bad request / validation error      |
| 401  | Unauthorized (no token)             |
| 402  | User not registered / invalid token |
| 403  | Forbidden / missing required field  |
| 404  | Resource not found                  |
| 409  | Conflict (duplicate resource)       |
| 429  | Rate limit exceeded                 |
| 500  | Internal server error               |

## Setup & Running Instructions

### Prerequisites

- Node.js >= 18
- PostgreSQL (or Neon serverless account)
- Redis server running locally or remotely
- Twilio account with SMS enabled

### Steps

```bash
# 1. Clone the repo
git clone <repo-url>
cd GrainSaathiBackend/Server

# 2. Install dependencies
npm install

# 3. Setup environment
cp .env.example .env
# Fill in all variables listed in Environment Variables section

# 4. Setup database
npx prisma generate
npx prisma migrate dev

# 5. Start Redis (if local)
redis-server

# 6. Start the server
npm run dev     # development (nodemon)
npm run start   # production
```

## Open Business Logic Questions (to decide)

1. **Can a farmer send gs_contracts to multiple buyers for the same crop simultaneously?**
   - If yes: need a mechanism to auto-cancel others when one is accepted.
   - If no: lock the crop until contract is resolved.

2. **What is the gs_contract expiry time?**
   - Suggested: 24-48 hours. After that, auto-expire and notify both parties.

3. **What happens after sell_contract is agreed?**
   - Is there a payment integration? UPI/bank transfer?
   - Is there a delivery tracking step?
   - Or is it purely a physical transaction with just a printed token?

4. **How is MSP (Minimum Support Price) enforced?**
   - Fetched from government APIs? Admin-configured? Per crop per season?
   - Should the platform block listings below MSP?

5. **Can an enterprise counter-offer a gs_contract?**
   - Or is it strictly accept/reject? Counter-offers add complexity but are realistic.

6. **What documents are required for trader/enterprise registration?**
   - GST certificate? Aadhar? PAN? Trade license?
   - Where are they stored? (S3, Cloudinary, local?)

7. **What is a gs_loginId?**
   - Is it a platform-generated username (like "GS-12345")?
   - Or just their phone number / email?

8. **Chat scope:**
   - Enterprise-to-enterprise only, or also trader-to-enterprise?
   - Is chat tied to a specific contract or general?
   - Message retention policy?

9. **Analytics for admin:**
   - What metrics? (daily registrations, active contracts, top traded crops, revenue?)
   - Real-time dashboard or periodic reports?

10. **Multi-language support?**
    - Target audience is Indian farmers — Hindi, regional languages?
    - API responses in multiple languages or just the frontend?
